# finance010 ALE-native submission

Generated by:

```bash
python tools/build_ale_delivery.py
```

The package has three distinct installation targets.

1. Copy `tasks/business_finance/bond_credit_ma_purchase_price/` into the ALE repository's
   matching `tasks/` path. It holds exactly `main.py` and `task_card.json`.
2. Publish or bake `task-data/business_finance/bond_credit_ma_purchase_price/base/` through the
   selected `task_data_source`. **`input/` and `software/` are staged before the agent;
   `reference/` must be staged only after the agent exits.** For this case that ordering is the
   entire secrecy model — see `environment-patch/BUILD_SNAPSHOT.md` §4.
3. Apply `environment-patch/`, build from the official `ale-ubuntu22` image, and register the
   result as `finance010-ubuntu22`.

The environment patch is additive. It must not replace the official CUA server,
`/opt/ale-run/.venv`, the Node runtime, the desktop startup path, or the image path conventions.

## Verify the generated package

```bash
python tools/build_ale_delivery.py --verify delivery/finance010-ale-submission
```

Verification is not a checksum pass. It re-derives the SHA-256 of every packaged file against
`MANIFEST.sha256`, then asserts the top-level layout, that the task directory holds exactly
`main.py` and `task_card.json`, that the adapter carries every required cua-bench hook, that the
card's task id / snapshot / runtime package / output contract match the contract in
`ale_case.yaml`, that `base/` holds exactly `input`, `reference` and `software`, that
`base/reference/` contains **exactly** the 23 declared evaluator files and nothing else, that no
private artifact is reachable from `input/` or `software/`, and that the card's `inputInventory`
still matches the packaged corpus file for file and byte for byte. Any one of those failing is a
non-zero exit.

## What is in the private layer, and why each file

`base/reference/` is the answer key. It is deliberately minimal — a file that the scorer does not
read has no business being in a directory whose whole purpose is to be withheld.

| Path | Read by |
|---|---|
| `case/scripts/` (12 modules) | the scorer itself |
| `case/main.py` | the lifecycle adapter `evaluate` is driven through |
| `case/task_card.json` | `case/main.py`'s `load()`; also the artifact `grounding_map.py`'s pointers name |
| `reference/EXPECTED.json`, `reference/traps.json` | `rubric_registry.py`, and nothing else |
| `00_task/output_schemas/` | `submission_reader.py` reads two; `grounding_map.py`'s pointers name four more |
| `00_task/TASK_PROMPT.md` | the prompt the card already carries verbatim; present so a `grounding_map` pointer resolves |

The case's other private artifacts — the trap design notes, the slice tie-out, the phase gate
reports, the hardening baseline, the positive fixture — are **not** shipped. They are authoring
evidence, not scoring inputs, and `ale/delivery.yaml` names each of them in
`forbidden_visible_names` so a future mis-staging into an agent-visible layer fails verification
rather than leaking quietly.

One thing the private layer does still carry: the twelve scorer modules cite this project's own
plan documents and requirement ids in their comments (`04-05-PLAN.md`, `SCORE-05`, and similar).
Those pointers do not resolve outside the authoring repository. They are left in place
deliberately. The modules are covered by a sha256 freeze in `reference/SCORER_FREEZE.json` whose
purpose is to keep difficulty measurements comparable across rounds, so stripping comments from
twelve of them would mean twelve freeze amendments for a cosmetic gain — and the comments are the
reasoning trail for the scoring logic, which is worth more inside an evaluator-only file than tidy
prose would be. The agent-visible layers (`input/`, `software/`) carry no such reference; that is
checked, not asserted.

## Runtime shape

The private tree is reassembled before scoring rather than scored in place. `case/scripts/`
resolves `reference/`, `00_task/` and `input/` by walking two levels up from itself, and ALE's
`base/` layout is fixed to exactly `input`/`reference`/`software`, so the staged private tree
sits one level deeper than the scorer expects. `tasks/…/main.py`'s `evaluate` rebuilds the
expected shape under a scratch root outside the agent's workspace, copying the staged corpus in
as `input/`, and removes it afterwards. The agent-visible tree is never written to.

## Known divergences from the finance001 reference submission

Stated here rather than left to be discovered:

- **Provider.** finance001 resolves its snapshot through gcloud; this case resolves
  `finance010-ubuntu22` through **docker**, because the brief mandates a network-isolated local
  sandbox and the `local:task-data` staging order is what removes the need for an encrypted
  reference archive. No image module ships for that reason —
  `environment-patch/REGISTRY_PATCH.md` explains when one would be required.
- **No input hash sidecar.** finance001 ships `POST_CONVERT_HASHES.json` inside its input tree.
  This corpus carries no such file, and adding one would change the agent-visible tree. Per-file
  hash integrity is enforced instead through the card's `inputInventory`, checked at build time
  by `--verify` and at run time by `software/verify_inputs.py --expect-corpus-digest`.
- **No `software` block in the delivered card.** The authoring card's `software.python` pins
  `pypdf==6.10.2` and `reportlab==4.4.10`, while the gated image manifest pins `pypdf==6.16.1`
  and ships no reportlab. Carrying that block would ship a claim the runtime contradicts, so it
  is dropped; `requiredSystemPackages` plus the runtime package's `install.sh` are what an
  operator installs from, and the prompt's own "Available tools" paragraph — which is accurate —
  is what the agent reads.
